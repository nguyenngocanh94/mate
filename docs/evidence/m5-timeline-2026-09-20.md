# M5 task 25: the timeline explains the acceptance

Task 25 of `docs/mvp.md`, measured 2026-09-20 on Herdr 0.8.2, Claude Code 2.1.278 (Mate) and codex-cli 0.154.0 (Crew).

The claim is M5's first question: a person who has never seen matev2 can read the run back out of `.matev2/matev2.db` alone - who did what, to whom, and why - without asking anybody.
The proof is the M4 acceptance flow run again with the observer recording, and then every claim checked against the database rather than against the code that filled it.
The data contract is `docs/timeline.md`.

## How it was run

```sh
LAB=fm-lab-matev2-w25-$$
(env -u CLAUDECODE herdr --session "$LAB" server >/dev/null 2>&1 &)
sleep 3
TMPDIR=$(realpath /private/tmp) MATEV2_LIVE=1 MATEV2_HERDR_LIVE_SESSION=$LAB \
  go test -count=1 -v -timeout 40m -run 'TestLiveTimeline' ./cmd/matev2/
herdr session stop $LAB; sleep 1; herdr session delete $LAB
```

`env -u CLAUDECODE` and a symlink-free `TMPDIR` are the section 7 lessons.
Each run got its own lab session, created for it and deleted after it.

The live test runs the `shop` manual half of `TestLiveAcceptanceTwoProjects`: the captain's ship request, the Mate spawning a Crew, the Crew asking, the captain handing the question over with `[assign]`, the Mate answering, the Crew handing back, and the captain merging from the Console.
That half exercises every source the ingest reads - two transcripts, the status file, `sent.log`, the `.meta` files and git - and leaves room inside the fifteen-minute budget for the assertions.
The `blog` auto half adds a second Mate and a digest but no source the timeline does not already see, and running both would put the test over the budget.

The observer, the daemon and the database handle are the ones `cmdConsole` builds (`consoleWatcherWithTimeline`), so what is proved is the shipped wiring and not a second one.

## The assertions, from the database

Printed by run 5:

```text
  "sha":"c5100b1a83ebaa98c6bab698dae15fefd307b4e3","short":"c5100b1","by":"captain","cause_rule":"crew.handback"}
mate:shop: 0 busy stretch(es) longer than 10s, all explained
crew:shop:buybtn: 1 busy stretch(es) longer than 10s, all explained
```

Each of those is read back out of the database and checked against the source, not against the ingest:

- **Every tool call has an action.** The test re-parses the very transcript the ingest read, with the same parser, and checks that every tool call it reports has an `action` row. What is being proved is that nothing is lost between the parser and the database.
- **Every status line has an event.** The test reads `crews/<id>.status` itself and checks a `status.appended` for each byte offset.
- **Every question was answered, after a positive wait.** `question.waited_ms` is measured from the crew's own `echo` (dated from its transcript) to the `sent.log` line that answered it.
- **The merge has a cause.** `merge.done` is derived from git, and `cause_rule` says which of the two rules fired.
- **No unexplained busy window.** For each actor, every ten-second window inside a stretch the observer saw as `busy` overlaps an action - a tool call, or a synthesised `thinking` action.

The Mate reports zero busy stretches because `internal/watch` polls the open crews of a project and not its Mate (task 18).
A Mate's busy time is explained by its transcript alone, which is the source that survives a rebuild anyway; this is written down in `docs/timeline.md` rather than left as a number a reader would misread as "the Mate was never busy".

## What the real data forced

### Herdr's `agent_session` is a Codex fact

Measured on the lab session of run 3, which had one Claude Mate and one Codex Crew:

```text
mate-shop  agent_session=None
crew-buy1  agent_session={'agent': 'codex', 'kind': 'id', 'source': 'herdr:codex',
                          'value': '01a0be02-6768-7fc1-8658-df01299fb705'}
```

`value` is exactly the uuid in the rollout's file name (`rollout-2026-09-20T…-01a0be02-….jsonl`), so one `herdr agent list` locates a Codex crew's transcript without opening a single file.
A Claude agent carries no `agent_session` at all, so the locator is two rules and not one: Claude goes by the Stop hook's `transcript=` and then by `session_id=` plus `~/.claude/projects/<slug>/<session-id>.jsonl`, Codex by `agent_session.value` and then by `harness.AdoptCodexRollout`.
`runtime.ObservedAgent` gained a `SessionRef` field for it, which is the only change this task made to `internal/runtime`.

Both fallbacks were exercised. In run 1 the Crew's agent was already gone by the time the assertions ran - the merge stops the crew and removes its worktree - and the rollout was still found by adoption on the canonical cwd; the locator then learned to reuse a path it had already resolved, so a later pass reads it off the `session` row instead of asking Herdr about every crew every five seconds.

### Codex's `exec` tool is JavaScript inside a JSON string

`custom_tool_call.input` is not a JSON object:

```text
"const r = await tools.exec_command({\"cmd\":\"echo \\\"working: …\\\" >> \\\"$MATEV2_STATUS\\\"\",\"workdir\":\"…\"});"
```

An ingest that did not unwrap the string recorded every Codex shell call's target as the escaping instead of the command.
The same tool is also how Codex edits a file: it sends a script that builds a patch, and the `*** Update File:` header sits inside a JavaScript string literal where the newlines are the two characters `\` and `n`.
A line-oriented reader finds no header there, so every Codex edit landed as an unnamed `patch`.
Both are fixed in `internal/timeline/transcript.go`, and the class of a patch call is corrected to `edit` so the story says `buybtn edits README.md` rather than `buybtn runs: …`.

### A status line's time comes from the crew's own shell command

`crews/<id>.status` has no timestamps, and the file's mtime is the time of its *last* line.
Dating every line by mtime puts the question after the answer the moment the crew writes anything else, and `waited_ms` goes negative on the first `matev2 reindex`.
The crew wrote each line with `echo "state: …" >> $MATEV2_STATUS`, and that is a tool call in its own transcript with a timestamp on it, so a status line is dated by the earliest shell action whose command contains it verbatim.
All three status lines of every passing run were dated this way (`dated_by: transcript.shell`); the mtime fallback did not fire once.

### A digest or an `[assign]` is in `sent.log` twice

Run 1 narrated the same `[assign]` twice, one second apart:

```text
15:40:43 the captain hands the Mate a question to resolve: "resolve: buybtn asked: …"
15:40:43 the captain hands the Mate a question to resolve: "resolve: buybtn asked: …"
```

That pair is not a bug in `sent.log`: section 7 already records it as the evidence the sentinel reached the model - one line written by the sender after the composer cleared, one by the Mate's own `UserPromptSubmit` hook.
But it is one handover, so the second copy is now recorded as the *reading* of the line (`channel: hook`, `"confirms": true`) and narrates as `the Mate reads it`.

### The trailing message group (run 2)

Run 2 failed with one of the Mate's ten tool calls having no action.
The cause is the parser's own contract: `harness.ParseTranscript` withholds a transcript's trailing message group because a later write may still extend it, so the last call of an agent that is still mid-turn cannot have an action yet.
The test was asking a live file a question only a settled file can answer.
The fix is in the test, not the ingest: it stops the observer and the daemon first, then re-ingests until the parser and the database agree, bounded at two minutes.
The ingest itself lost nothing - which is exactly what the corrected assertion proves.

### A branch is too short-lived to be the only witness (run 4)

Run 4 failed with `no merge.done event was recorded within 2m0s`, after a merge that plainly happened (`shop/buy1: merged 1 commit(s) into main (e02536c..4b5b722)`).

`merge.done` was derived from git alone: the crew is closed `finished` and its branch tip is now an ancestor of the default branch.
But `matev2 merge` deletes the branch on its way out, so the tip has to have been read *before* the merge - and the crew committed six seconds before the captain merged.
The observer's cycle is the five-second sleep plus the round itself, so a six-second window is one a poll can miss, and run 4 missed it.
Run 1 caught it; that is the difference between the two, and it is luck, not design.

The fix is a second source for `git.committed` that does not expire.
Git echoes the sha back at the crew - `[matev2/buybtn c5100b1] docs: link Buy to existing express checkout route` - and that line is in the crew's transcript for ever, so a shell action that ran `git commit` and got that echo names a commit, which is then read out of git by its sha.
Run 5's `16:08:41 buybtn commits c5100b1 …` is that rule firing: the commit and the merge happened nine seconds apart and the timeline has both.

### `event` needed a natural key

A transcript is re-read whole on every pass, for the reason above.
Without a key, the same fact would become a second row with a second id every five seconds, and a dashboard following `event.id > ?` would replay history as news.
One column was added to the M5 schema: `event.dedup TEXT NOT NULL UNIQUE`, the natural key of the fact.
Every other table is keyed by whatever produced it - a transcript path and a record's source ref, a log path and a byte offset - so no other table needed one.

## Reindex

`matev2 reindex <workspace>` empties every derived table and rebuilds from the files and the transcripts inside one transaction, so a rebuild that fails halfway leaves the timeline it started with (`TestAFailedReindexLeavesThePreviousTimelineInPlace`).
Two rebuilds of the same sources are byte-identical, `event.id`s included (`TestReindexingTwiceProducesAByteIdenticalStory`), which is what lets a reader quote an id.

The unit fixtures are excerpts of the M4 acceptance run of 2026-09-19, captured from the real transcripts and trimmed to their bulk only: `internal/timeline/testdata/claude-2.1.278-transcript.jsonl` (12 assistant message groups, 11 tool calls) and `codex-0.154-rollout.jsonl` (11 `token_count` records, 9 tool calls).
The token totals asserted against them are read out of the files with `jq`, not out of the ingest: the Codex turns' deltas add back up to the rollout's own last `total_token_usage` (232,424 input / 209,152 cached / 1,544 output / 351 reasoning), and the Claude turns' add up to the first eleven message groups' usage.

## What is not proved here

`mode.changed` and `health.changed` are observations of a moment that leaves no file behind, so a rebuild recovers neither.
`docs/timeline.md` says so, and it is the honest shape of a flag with three owners and a poll loop that keeps nothing.

The auto half of the acceptance - a daemon digest reaching the Mate - is covered by task 19's own live test and by the unit fixtures, not by this one.

`review.started` has no producer: the kind is in the vocabulary because the Mate's `reviewing(crew)` scene is task 26's.

The scene machine, `transition` and a filled `v_now` are task 26's; the view exists with its columns so task 26 changes no consumer.
`pricing` and `v_task_ledger.cost` are task 27's; the ledger joins `pricing` already and reports `NULL` cost until there is a row, because a missing price is not a price of zero.
