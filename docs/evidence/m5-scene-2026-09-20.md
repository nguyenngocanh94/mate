# M5 task 26: the office scene, read out of the data

Task 26 of `docs/mvp.md`, measured 2026-09-20 on Herdr 0.8.2, Claude Code 2.1.278 (Mate) and codex-cli 0.154.0 (Crew).

The claim is M5's second question: the scene changes are an explicit state machine, every edge names the event that fires it, and no event of a real run falls outside it.
The proof is the same acceptance flow task 25 recorded, projected onto the office and then read back as a story.
The machine is written out in `docs/timeline.md` section 9; this file is what it produced on a real run.

Four things are checked, and each of them is read back out of `transition` rather than out of the projection that wrote it:

- **No `unexplained` transition.** An event that reaches an actor's machine and matches no edge is recorded with `unexplained: <kind>` in `detail` rather than dropped, so this assertion is the whole point of the projection: every event of a real run either moves somebody or is a row of the table that says it moves nobody.
- **Every state a ship task passes through is reached.** `arriving`, `at_desk_working`, `walking_to_ceo`, `waiting_at_ceo`, `waiting_review`, `leaving`, `gone` for the crew; `idle`, `on_phone`, `receiving_digest`, `reading`, `deciding`, `answering` for the Mate.
- **Every wait at the CEO's door is a measured stretch that ends at the desk.** The scene's 1m7.41s and the `question` table's 67410ms are the same number measured from two different tables - the transitions, and the question row the inbox rule filled - which is what makes either of them worth quoting.
- **Every transition names the event that caused it**, so a reader who doubts a move can read the fact behind it.

## What the real run forced

### The Mate's turn is caused by the hook's echo, not by the `[assign]`

Run 1 failed on `nothing in the run put anybody in reading`, in a run where the Mate plainly read the captain's note and answered the crew forty seconds later.

The edge as first written said: a Mate turn whose cause is an `[assign]`, a digest or the question one carried is the Mate picking the note up.
The causality rule of `docs/timeline.md` section 5 gives every Mate turn the **last line that reached its composer** as its cause - and on a Claude Mate that is not the `[assign]`.
The Mate's own `UserPromptSubmit` hook writes the same line back to `sent.log` when the model reads it, so the newest line to the Mate is the echo, whose kind is `message.sent`.
Run 1's `sent.log`, unchanged:

```text
09:47:57 | app   → mate     | resolve: buy1 asked: "choose checkout target: …"
09:47:57 | app   → mate     | resolve: buy1 asked: "choose checkout target: …"
```

and the turn that read it started at 16:48:05, eight seconds later.

The fix is two edges instead of one, and both are better than what they replace.
`mate.reads` no longer looks at the cause at all: it fires from `receiving_digest`, because the note is on the desk until a turn picks it up, and the state is the thing that knows it.
`mate.reads.echo` takes the hook's echo for what section 4 already says it is - the one fact in `sent.log` that proves the model read what matev2 typed - and narrates it as the Mate reading the note, which is exactly what the event narration has said since task 25 (`the Mate reads it`).
Run 2's `16:53:40 matev2 walks the captain's note into the Mate's office` / `16:53:41 the Mate reads buy1's note` is that pair firing one second apart.

A Codex Mate has no such hook and leaves no echo; it picks the note up at its next turn through `mate.reads`, and the scene reads the same for both harnesses.

### One model call is one turn, so the CEO blinks

`turn.ended` returns the Mate to `idle`, which is what M5 question 2 asks for, and a turn is one model call in both harnesses (`docs/timeline.md` section 4).
A Claude Mate working through one prompt therefore goes `deciding` → `idle` → `deciding` several times in a row, which is eleven of run 2's thirty-four transitions.
It is not noise: each of those rows points at a real `turn.started` or `turn.ended`, and a renderer that wants the coarser unit has `turn.harness_turn_ref` - one prompt and everything it caused - already in the `turn` table.
Smoothing it inside the projection would mean the machine looking ahead to see whether another call of the same harness turn follows, and a fold over an event stream that looks ahead is not a fold.

## What this does not prove

`reviewing` and `merging` are the Mate's two states this flow cannot reach, and the test says so rather than pretending otherwise.
The captain reviews the diff in the Console and merges from it, and neither gesture writes to any file (docs/mvp.md section 7), so `merge.done` carries `by: captain` and the Mate never had the work in its hands.
Both states are covered instead by the scene package's own table-driven cases, which drive `review.started`, a Mate turn running `matev2 diff shop k3`, and a `merge.done` with `by: mate`.

`asleep` and `blocked` are not in this run either: the observer found nothing wrong with a crew that was never silent for three minutes.
They are exercised by the fixture depth test in `internal/timeline`, which appends the `incidents.log` lines a slower run leaves behind and checks that the crew goes back to exactly where the incident found it - including a crew that falls asleep standing at the CEO's door and is still waiting when it wakes.

`leaving(closed)`, `leaving(failed)` and the Mate's `gone` are the same: real shapes, not reached by a run that ends in a merge, and covered by the table-driven cases.
